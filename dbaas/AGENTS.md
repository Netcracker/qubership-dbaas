# AGENTS.md (dbaas)

`dbaas-aggregator` is a Quarkus REST service (`/api/v3/dbaas/*`, package `com.netcracker.cloud.dbaas`), layered as
`controller` → `service` → `dao`/`repositories` → JPA entities. It routes requests over HTTP to per-type database
adapters (PostgreSQL, MongoDB, Redis, Cassandra, OpenSearch, ClickHouse, ArangoDB). Registrations are
namespace-isolated and identified by a classifier. PostgreSQL is the system of record, H2 an in-memory read mirror.
`dbaas-integration-tests` are black-box tests (OkHttp) against a deployed cluster.

Full rules: [aggregator guidelines](../docs/development/aggregator.md) and
[testing and CI guidelines](../docs/development/testing-and-ci.md).

## Backward Compatibility

The aggregator publishes REST APIs and the adapter contract that database adapters implement. All of them are contracts:
the operator, the client libraries, the external consumers and the adapters depend on them.

Existing endpoints, fields, filters and error codes keep their meaning; a new field is optional and appears in
all specs and docs in the same change.

## Do

- Put `@RolesAllowed` on every endpoint: auth is Basic or a Kubernetes service-account JWT, and an unannotated
  endpoint is denied.
- Use constructor injection and `@ApplicationScoped` for new CDI beans; put `@Transactional` on service methods only.
- Map DTOs with MapStruct mappers in `mapper/` (`componentModel = "cdi"`); keep Lombok before MapStruct in
  `annotationProcessorPaths`.
- Name new Flyway migrations `V1.NNN__<Description>.sql` with the next free number; keep the H2 schema in sync for
  mirrored tables.
- Build `Database` / `DatabaseRegistry` test fixtures with `DatabaseBuilder`; name tests `test<Logic>_<Condition>`.
- Tag new `*IT` tests with DB-type and area tags when applicable.
- Update `docs/api/rest-api.md` with API changes.

## Don't

- Don't edit or rename existing PostgreSQL Flyway migrations.
- Don't hand-write DTO converters when a MapStruct mapper covers the case.
- Don't add `@Transactional` to DAOs or REST controllers.

## Generated Files

Never edit these by hand:

| File                             | Regenerated by                                                                                                          |
|----------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| `docs/api/adapter-contract.yaml` | `mvn -pl dbaas/dbaas-aggregator -am process-classes` (`swagger-maven-plugin`, `process-classes` phase)                  |
| `docs/api/OpenAPI.json`          | `mvn -pl dbaas/dbaas-aggregator test -Dtest=SwaggerOpenApiDocsTest`, which writes the served `/v3/api-docs` to the file |

Commit the result. Every aggregator test run rewrites `docs/api/OpenAPI.json`, so a modified file after `mvn verify` is
expected when the API changed. `docs/api/rest-api.md` has no generator; edit it by hand.

## Testing

- Unit tests: JUnit and Mockito. Component tests: `@QuarkusTest` with Testcontainers PostgreSQL.
- Integration tests run against a deployed stack and are skipped by default (`skipIT=true`). They also do not fail the
  build (`dbaas-integration-tests/pom.xml` sets `maven.test.failure.ignore=true`), so read
  `dbaas-integration-tests/target/failsafe-reports`.
- Run the integration tests on a stack from `bootstrap/helmfile`; CI runs them automatically only for `chore(deps)` pull
  request titles (`test-it.yml`), so start that workflow by hand when a change needs them (requires approval).

## Commands

After any change to the aggregator, run `mvn -B verify`; it must pass. The commands below exist for a faster loop.

```bash
mvn -B verify                                                   # build and test
mvn clean package -DskipTests -pl dbaas/dbaas-aggregator -am    # build the aggregator only
mvn test -pl dbaas/dbaas-aggregator -Dtest=<ClassName>          # one test class
docker build -f dbaas/Dockerfile -t dbaas-aggregator:latest .
```
